✦ VipKorner Design System · v1.0.1

Midnight Marquee

A production design system for vipkorner.app: tokens, a proven responsive layout layer, and a visual compatibility layer keyed to the class names the app already uses. Content is the only bright thing on screen. Gold is the metal. Everything else recedes.

Overview

Layered CSS

The production app separates responsive geometry from appearance. The layout layer preserves the tested desktop, compact and mobile behavior; the reskin targets those same selectors without redefining the app grid.

FileWhat it isWhen you touch it
vipkorner-tokens.cssPrimitives and semantic aliases. The only place a colour, size, duration or z-index is invented.Adding or retiring a design decision. Rare, and reviewed.
vipkorner-layout.cssResponsive page geometry, sizing, positioning, overflow and breakpoints restored from the proven pre-reskin app.Changing layout or responsive behavior.
vipkorner-reskin.cssVisual-only compatibility rules for color, borders, type and elevation.Changing appearance without changing geometry.
vipkorner-theme.cssOriginal full reference theme retained as the component specification; production does not import it.Auditing component coverage.
tokens.jsonThe same tokens, machine-readable — for a Tailwind theme extension, a Figma sync, or a lint rule.Wiring tooling.
index.htmlThis page. Its specimens are rendered by the two stylesheets above, not by copies.Reviewing. If a specimen looks wrong here, it is wrong in the app.

The one rule that matters. Components reference semantic tokens. Semantic tokens reference primitives. Primitives are the only literals. If a component needs a colour that has no semantic name, the colour is missing from the system — add it to the token file, don't inline it.

Installation

Import order is load-bearing
/* app/globals.css */
@import "tailwindcss";
@import "../design/system/vipkorner-tokens.css";   /* primitives + semantics */
@import "../design/system/vipkorner-layout.css";   /* responsive geometry   */
@import "../design/system/vipkorner-reskin.css";   /* visual compatibility  */

/* Nothing else. Any rule that survives below this line is a migration
   leftover — track it down and delete it. */

Tokens must load after Tailwind's preflight, followed by the responsive layout and then the visual reskin. The token file ends with a legacy bridge that maps the nine variables the layout uses (--ink, --accent, --plum…) onto the new system. The split is intentional: the layout owns geometry; the reskin owns appearance.

--plum is deliberately bridged to gold. If any purple appears after installation, something is bypassing the token layer.

One gotcha found while building this. The current stylesheet writes font-family: var(--font-geist), Arial, sans-serif. --font-geist is injected by next/font at runtime — and if it is ever absent (a static export, a stylesheet loaded outside a Next render, a font-loading failure), var() with no fallback makes the entire declaration invalid at computed-value time and every element in the app silently reverts to the browser's default serif. The token file writes var(--font-geist, system-ui) instead. Worth fixing in globals.css today regardless of whether this system ships.

Color

Foundations

Do
Use gold for the one action you want taken on a screen. Use rose only where the app is expressing feeling or urgency — a like, an unread count, an active Short ring. Use ember only as the far stop of a gradient it shares with gold.
Don't
Put gold and rose in the same button row as two competing primaries. Use ember as a standalone signal — at 6.34:1 it reads as "warning" to people who can't distinguish it from gold. Introduce a fourth hue without retiring one.

Why no blue for "info". Adding a cool hue to a warm palette on a near-black canvas costs more than it returns — it reads as a system alert from a different product. Informational states use gold at low opacity (--vk-brand-subtle). Teal is excluded by constraint; purple is retired with --plum.

Media on a dark canvas

The problem this direction creates

VipKorner is a photo and video product, and its users control the content. On a light canvas a dark photo has an edge. On near-black, a photo with dark corners dissolves into the page — the card loses its shape, and a portrait shot at night looks like a rendering bug. Three rules handle it.

1 · Hairline

Every media surface carries --vk-media-hairline: a 6%-white inset ring. It costs nothing on a bright photo and rescues a dark one.

2 · Letterbox

Letterbox bars use --vk-media-bg #1C1C22, never black. Black bars read as broken; a lighter well reads as a frame.

3 · Scrim
Text over media

Text over media always sits on --vk-scrim-bottom or --vk-scrim-top. Contrast against an unknown photo can't be computed, so it's guaranteed structurally instead.

Test with real uploads before shipping. A dark-canvas redesign roughly doubles the visual QA surface for user media: night photography, screenshots with white backgrounds, portrait video with black bars, and transparent PNGs all behave differently than they do today. This is the single largest risk in Option A, and it is not a risk the token layer can retire on its own.

The 11px floor, and why it moved. The current stylesheet uses 9px 24 times, 10px 34 times, 8px five times and 7px once — meaning a large share of the interface sits below comfortable reading size, including timestamps, comment counts and menu items people are expected to act on. Under this system 11px exists only for uppercase, 700-weight, .16em-tracked labels — a shape you read as a marker, not as a sentence. Anything a person must read to operate the app is 12px or larger. This is the change that will require the most edits, and the one users will feel most.

Elevation

Shadow plus hairline, always

On a near-black canvas a drop shadow is nearly invisible — there is no light to occlude. Every level therefore pairs a shadow with a 1px light ring: the ring does the separating, the shadow does the depth. Shipping one without the other is the most common dark-mode mistake.

Motion

Named for the gesture

Five durations, four easings. A transition names the gesture it serves rather than a number, so the same interaction feels the same everywhere in the app.

Reduced motion is not a null case. Under prefers-reduced-motion everything collapses to 0.01ms — but the Short progress bar is a timer, not decoration. It snaps to full instead of vanishing, so a person who can't see the animation still knows where they are in the sequence. Auto-advance keeps working.

Tap targets — two sizes, and only two. --vk-tap-target: 44px is the default for every standalone control (WCAG 2.5.5 AAA, and the platform touch convention). --vk-tap-compact: 38px is permitted only in dense inline rows — card action pairs, viewer toolbars, modal header buttons — and is still well above the 24px WCAG 2.5.8 (AA) floor. The current stylesheet has controls at 30, 32, 34 and 36px; all of them resolve to one of these two. Nothing lives between them.

Where a control must look small — the settings toggle is 46 × 27px — the hit area is expanded with a pseudo-element (.toggle::after { inset: -9px -4px }) rather than the target being shrunk to match the drawing. Use that technique anywhere else the same tension appears.

Private account

Only approved followers can see your posts and Shorts.

  • Every input is 44px minimum and sits on --vk-surface-raised, one step lighter than the panel behind it. On dark, a field that matches its container disappears.
  • Focus does two things: the gold outline ring (12.64:1) plus a border-colour change to brand. Ring alone is invisible to someone using a high-contrast OS theme; both together survive it.
  • Errors are text, not colour. .inline-error in red-300 (8.11:1) states what's wrong and what to do — paired with aria-invalid and aria-describedby.

  • Never disable a submit without saying why. A greyed button with no explanation is the most common accessibility failure in a signup flow, and this app has an invitation gate where it matters most.

Be precise about what a stylesheet can promise. The token and theme layers can guarantee contrast, focus visibility, target size and motion. They cannot supply alt text, manage focus, or announce state. Those three rows are real work in page.tsx, and adopting this system does not do them. They are in the adoption plan below as their own phase.

One product-specific note: VipKorner's Short player is time-based, and WCAG 2.2.1 asks that time limits be adjustable or extendable. Auto-advance with no pause control is a genuine failure. A tap-and-hold pause already matches user expectation from the category — worth confirming it exists.

Adoption plan

Five phases, each shippable

Each phase leaves the app in a working, deployable state. No phase requires the next one to land in the same release.

1
Install tokens and preserve the proven layout

Load vipkorner-tokens.css before vipkorner-layout.css. The bridge maps the legacy variables onto the new palette while the tested responsive geometry remains intact.

2
Apply the visual compatibility layer

Load vipkorner-reskin.css last. It may change color, type, borders and elevation, but must not redefine the app shell grid, page widths or responsive breakpoints. Validate every page at desktop and mobile widths before deployment.

3
Fix the type floor

The 9px and 10px text becomes 11px micro labels or 12px meta. This is a real visual change: some rows get taller and some truncation thresholds move. Do it as its own PR so it can be reviewed on its merits rather than buried in a redesign.

4
Split page.tsx and do the component-level accessibility work

One file per view, one file per modal. While the components are open: alt text, focus trapping and restoration, Esc handling, live regions for unread counts and toasts, Short pause. These are the three failing rows in the table above.

5
Delete the bridge and add the guard

Remove the legacy variable block. Add a lint rule (Stylelint declaration-property-value-disallowed-list, or a CI grep) that fails any raw hex or raw px outside the token file. Without this step the system erodes within two sprints — that is how the current 155 literals accumulated.

What is deliberately not in the plan. No functional change, no route change, no API change, no schema change, and no change to the invitation flow, the server-side 18+ check, the self-scoped follower endpoints, block and privacy controls, Short expiry or text-only DMs. This is a presentation system.

Governance

How it stays true
Adding a token
Name the role, not the appearance — --vk-text-subtle, never --vk-grey-3. Compute its contrast against all four surfaces before it lands, and record the numbers in tokens.json. If an existing token is within 5% of the new one, use the existing one.
Rejecting a token
"It looks slightly better here" is not a reason. A new hue, a fourth family, a shadow between elev-2 and elev-3, or a colour whose only justification is one screen — all no. Every added token is a decision the next person has to understand.

Review checklist for any UI PR

  • No raw hex, rgb or px outside vipkorner-tokens.css.
  • Every interactive element reaches 44px and has a visible focus state.
  • Any new colour pairing has a computed contrast ratio in the PR description.
  • No new text below 12px unless it is an uppercase tracked micro label.
  • New motion uses a named duration and easing, and degrades under prefers-reduced-motion.
  • Any state expressed with colour is also expressed with a word, an icon, a weight or a position.
  • Tested with a real dark photograph, a real bright screenshot, and a portrait video.

Out of scope & open questions

Honest edges
  • The marketing site (vipkorner.com) is not covered here. It is one self-contained file with its own <style> block; it should consume vipkorner-tokens.css and get a small site-specific theme rather than being folded into the app theme.
  • Email templates — the confirmation email is part of the invitation flow and currently has no design coverage. Dark-mode email is its own problem; it needs a light-canvas variant of the palette.
  • A light theme. The token structure supports one — redefine the semantic block under a [data-theme="light"] selector and nothing else changes. Whether to build it is a product call; a photo-sharing app that people open at night has a real argument for dark-only.
  • Iconography. The system standardises size and stroke for the 30 lucide icons in use but does not define a custom set. If VipKorner wants a proprietary mark language, that is a separate piece of work.
